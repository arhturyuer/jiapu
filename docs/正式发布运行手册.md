# 有谱正式发布运行手册

> 文档状态：现行规范。本文描述发布要求，不证明线上配置已满足；核验依据见[文档索引](./文档索引.md)。环境授权以 [AGENTS.md](../AGENTS.md) 为准。

## 一、职责与发布门槛

AI 负责开发、测试，以及获授权环境中的云函数、索引、安全规则、任务配置和运营后台部署与回读。人工负责平台专属配置、小程序上传、体验版设置、提交审核和正式发布。AI 不调用上传、提审或发布操作。

流程：本地检查 → staging 服务端部署及验收 → 当前请求明确授权 production → AI 部署生产服务端并验证 → 人工上传和体验版复验 → 人工提交审核 → 人工发布及发布后冒烟。

每次 production 操作必须同时满足：

1. 本版本已在独立 staging 完成与改动匹配的部署和验证，包括自动化测试、构建及必要功能验收。
2. 发布负责人在**当前请求**中明确授权 production、生产发布或部署生产；历史记录仅保存证据，不能代替当前授权。
3. 生产命令通过仓库现有目标和确认护栏，不修改、删除或绕过护栏。
4. 新服务端兼容当前正式客户端与待审客户端；有数据变更时说明迁移及回滚限制。

未满足生产门槛只能执行获授权的 staging 工作。备份、恢复演练、平台资质和告警属于持续运维要求；常规版本按改动风险核验，不机械要求执行初始化或全量数据操作。

## 二、AI 服务端交付

每次使用[交接模板](./releases/TEMPLATE.md)，记录版本、代码提交及未提交改动、实际环境、部署组件、验证结果、回滚版本、文档更新和人工待办。开始云端操作前报告目标，结束后报告实际目标与验收入口。密钥值不进入日志或文档，staging 实际 ID 保留在受控本机记录。

### staging

首次配置见[staging 建立手册](../deployment/staging-runbook.md)。运行 `./deployment/staging-preflight.sh`；日常按改动选择 `./deployment/deploy-staging.sh functions`、`indexes`、`security`、`hosting`，随后执行 `verify` 和相关功能验收。`all` 包含 bootstrap，适用于首次完整初始化或明确需要这些步骤的变更，不是每次迭代的默认动作。

只使用虚构资料与 staging 测试账号。跨环境共享的平台消息绑定若会影响 production，必须先获得当前请求的生产授权，不能因 staging 验收中断生产服务。

### production（仅当前请求明确授权后）

生产目标以 `deployment/target-guard.mjs` 为准。小程序 `develop` → staging，`trial` / `release` → production，未知值 → staging；不得删除 `env.local.js` 或修改 `env.js` 来临时切环境。

- 生产预检：`PREFLIGHT_MODE=production ALLOW_PRODUCTION=1 TARGET_ENV_ID=cloud1-d5gs5yj4l283d9c6d ./deployment/preflight.sh`。预检中的微信预览仍为 develop/staging，不能作为生产真机验收证据；生产预检不允许跳过预览。
- 云端写入继续要求 `DEPLOYMENT_TARGET=production ALLOW_PRODUCTION_CHANGE=1` 及正确生产 ID。涉及任务派发或触发器时，先运行 `deployment/configure-production.mjs` 回读并保留现有用户函数密钥，再使用生成的 `deployment/cloudbaserc.production.local.json` 部署 `youpuUserApi` 与 `youpuJobs`；普通全函数代码部署仍使用 `uploadCloudFunction.sh <环境ID>`。旧通知函数与 V2 的消息绑定不会因代码部署自动变更。
- 支付通知活动目标应为 `youpuPaymentNotifyV2`，源码来自 `cloudfunctions/youpuPaymentNotify`；staging 仍用 `youpuPaymentNotify`。旧通知函数的实际绑定/调用需回读，不擅自删除。
- 按变更应用索引和安全规则并回读；仅首次初始化或明确涉及集合/schema 变化时执行受密钥保护的 bootstrap。不得因普通发版创建初始账号或清空集合。
- 回读四个活动函数的 Nodejs20.19、超时、内存、变量键、OpenAPI 权限和触发器。确认用户函数具备异步调用 `youpuJobs` 的运行角色权限，且 jobs 只保留 `youpu-retention-maintenance`。`verify-cloud.mjs <环境ID>` 检查运行配置；运行角色权限和平台事件绑定另按实际平台结果核对。
- 运营后台用明确的生产 `VITE_CLOUDBASE_ENV` 构建，再部署到同一目标静态托管并验证登录与 API；不能上传 staging 构建产物。托管操作同样受当前生产授权约束。
- PRIVATE 存储基线需 `ALLOW_PERSONAL_PRIVATE_STORAGE=1` 显式确认并回读；不将权限降级成公开读写。索引和规则命令见[开发部署说明](./有谱开发部署说明.md)。
- 核验存储生命周期没有对整个 `staging/` 对象前缀做 24 小时删除；该前缀包含审核通过的图片，旧手册的整前缀清理指令已废弃。发现误配时按当前授权处置并检查受影响媒体，不能擅自执行生产恢复。

### 会员虚拟支付（涉及时）

1. staging Android 沙箱完成三个固定商品、推送发货、重复推送、查单兜底和退款验收，详见[会员验收手册](./家庭会员staging验收手册.md)。
2. production 的 `youpuUserApi` 配置 VP_APP_ID、VP_APP_SECRET、VP_OFFER_ID、VP_APP_KEY、VP_INTERNAL_NOTIFY_SECRET、JOB_DISPATCH_SECRET 和 JOB_FUNCTION_NAMESPACE；`youpuJobs` 配置相同的 JOB_DISPATCH_SECRET；V2 通知函数仅配置 VP_INTERNAL_NOTIFY_SECRET。用户 API 的 PAYMENT_MODE 应为 live；密钥仅存目标环境。
3. 回读 schema v8、会员集合/索引、权限和函数规格。通知函数 20 秒/512 MB，jobs 900 秒/512 MB；jobs 只保留每日 `youpu-retention-maintenance`，导出和家庭备份由用户请求异步派发。
4. 人工核实三个一次性商品 `youpu_vip_30d`、`youpu_vip_365d`、`youpu_vip_life` 及 Android/iOS 所需资质。保留云函数 JSON 推送协议，不恢复 HTTP 回调，不配置订阅专用退款事件。
5. 人工核实 `event/xpay_goods_deliver_notify`、`event/xpay_refund_notify` 的实际绑定；每个事件组合只绑定一个环境/函数。切换前清理原环境待确认订单，production 目标为 V2。记录绑定证据，不输出密钥。
6. 人工体验版中 Android/iOS 各完成最低金额商品真单及真实退款，验证到账、共享、重启恢复、幂等、退款权益回收和账单。真实交易属于本次验收范围时才执行，不能用本地测试替代。

## 三、人工小程序上传、审核与发布

1. 核对服务端交接完成、当前授权、版本、源码状态和旧客户端兼容证据。
2. 在 `miniprogram/config/release-notes.js` 首项准备 `{ version, summary }`；**人工**执行 `bash deployment/upload-miniprogram.sh production <版本号>`，脚本校验版本与路由并使用摘要作为上传描述。
3. `staging` 参数只校验 develop 路由，不生成隔离的体验包。人工设置体验版后实际连接 production，使用生产测试账号完成相关真机复验。
4. 人工在微信公众平台提交审核，记录审核结果；通过后由人工决定并执行正式发布。上传、提审、审核通过均不等于已发布。
5. 发布后验证 release 实际目标、关键功能、错误率与待处理任务，观察至少 30 分钟并记录结果。遇到失败停止后续发布步骤，按已验证方案处置。

## 四、数据与长期运维

备份恢复、清理、迁移均需在本次授权中明确范围。对高风险变更，先记录集合和存储范围、索引、函数版本与密钥版本（不导出明文），确认恢复点和独立备份，并在独立目标演练恢复后再执行变更。

- 备份目标：每日保留 30 天；平台保留期不足时制定独立备份方案，不能默认已配置成功。
- 旧 `backup_manifests` 仅记录集合计数且已停止生成，不是可恢复的数据备份；真实备份继续依赖平台备份或经批准的独立导出方案。
- 验证集合、计数、人物/关系关联、媒体和唯一索引；账号与权限重新校验。
- 迁移不默认清空旧集合；如确需清理，必须单独明确目标、可恢复证据和授权。禁止覆盖唯一可用副本。
- 冻结写入、停止触发器等只在具体变更确有需要时实施，记录恢复服务的步骤与结果。

以下为运维目标，实际告警是否已配置或触发需平台核验：

| 指标 | 阈值 | 处置 |
|---|---|---|
| 5 分钟错误率 | > 2% | 停止后续发布，按 requestId 排查 |
| API P95 | > 2 秒 | 检查查询、索引、审核与配额 |
| 审核队列最老任务 | > 30 分钟 | 检查回调与复核任务 |
| 数据库/函数/存储用量 | > 80% | 检查增长与扩容需求 |
| 注销 failed | 任意新增 | 受权限控制重试，留审计和排查记录 |
| 家谱 deleting | 超过 30 分钟 | 检查任务续跑，必要时人工介入 |

用户、运营与任务函数保留 requestId、匿名 actorId、action、durationMs、success、resultCode 日志，不记录个人资料、原始 openid、令牌或媒体地址。

## 五、回滚与遗留项

- 小程序：由人工按平台可用能力回退已验证版本，复验 release 环境与服务端兼容性；不回滚已成功提交的业务事务。
- 服务端：回退与现有数据及仍在用客户端兼容的代码版本，保留故障证据；不能默认改为旧 `familyFunctions`。
- 后台：回退同环境静态站点版本并验证登录/API，运营人员不能直接改库代替修复。
- 任务：用户触发任务按 taskId 事务抢占；故障时保留状态和 requestId，修复后重新申请或受控续跑。每日保留任务需要时可暂停唯一触发器，恢复后回读验证。
- 支付：保留云函数通知协议和正确绑定，处理完待确认订单，再回退兼容代码；不改回 HTTP 路由。
- 数据损坏：停止受影响写入，按已授权恢复方案在独立目标校验后切换，禁止直接覆盖唯一副本。

生产稳定观察期不少于 7 天，但经过时间不等于旧服务已无调用。`familyFunctions`、旧通知函数的流量、绑定和客户端依赖必须另行核验；只有证据充分且获得对应变更授权，才考虑停用或应用 `function-rules-after-stabilization.json`。
